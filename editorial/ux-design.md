# UI/UX 설계

> 상태: **설계 초안.** 시스템 구조는 [platform-architecture.md](platform-architecture.md), 로드맵 구조는 [roadmap-design.md](roadmap-design.md).

## 1. 이 서비스의 UX가 풀어야 할 문제

1. **분량이 크고 순서가 하나가 아니다.** 190개 장을 처음부터 읽는 독자는 없다. → **지도와 경로**가 핵심 내비게이션이다.
2. **읽는 책이 아니라 훈련하는 서비스다.** 장은 실습·퀴즈·통과 기준으로 끝난다. → **직접 해 보기와 진행도**가 화면의 중심이다.
3. **이론과 실습이 한 화면에서 서로 반응해야 한다.** 수식을 읽고, 위젯을 조작하고, 코드를 고쳐 돌리는 일이 끊기지 않아야 한다. → **연결된 표현**(linked representations)이 설계의 중심 원리다.

## 2. 상호작용 원칙

### 2.1 연결된 표현: 수식 · 위젯 · 코드 · 그림이 같은 상태를 본다

한 페이지의 위젯과 코드 셀은 **페이지 상태 버스**를 공유한다. 위젯이 내보내는 변수(`data/widgets.toml`의 `binds`)는

- 본문 수식에 실시간으로 채워지고 (예: $\mathbf{A} = \begin{bmatrix}1 & 0.5\\0 & 1\end{bmatrix}$가 끌 때마다 갱신)
- 같은 세션의 코드 셀에 같은 이름의 변수로 주입되며
- 코드 셀이 값을 바꾸면 위젯이 다시 그려진다.

예: 7.2장에서 학습자가 `linear-map-2d` 위젯의 basis 벡터를 끈다 → 수식의 $\mathbf{A}, \mathbf{b}$가 바뀐다 → 아래 코드 셀 `f(np.zeros(2))`를 다시 돌리면 $\mathbf{b}$가 나온다 → bias 토글을 끄면 격자가 원점을 지나 다시 그려진다.

### 2.2 예측 → 관찰 → 설명

핵심 개념마다 **먼저 예측하게** 한다. 본문 중간의 `::quiz{id="..."}` 한 문항에 답한 뒤에야 위젯 애니메이션이나 코드 결과가 열리고, 해설이 예측과 결과의 차이를 설명한다. 단순한 시연보다 학습 효과가 크고, 퀴즈가 본문의 흐름 안에 자연스럽게 놓인다.

### 2.3 모션은 설명할 때만

| 쓰는 곳 | 예 | 규칙 |
|---|---|---|
| **과정 설명** | 역전파의 gradient 흐름, SVD의 회전–스케일–회전, 확산의 forward/reverse, 학습 루프 단계 | 항상 **재생·일시정지·한 단계·되감기** 컨트롤. 학습자가 속도를 지배한다 |
| **상태 전이** | 격자 변형 보간, 사전→사후 분포 갱신 | 시작과 끝 상태를 모두 정지 화면으로 볼 수 있어야 한다 |
| **스크롤 연동** | 긴 유도(derivation)를 단계별로 강조 | 스크롤을 되돌리면 그대로 되돌아간다 |
| **UI 피드백** | 퀴즈 정답·오답, 실행 완료, 진행도 갱신 | 짧게(≈200–300ms), 의미 있는 변화에만 |

- 장식용 모션(배경 애니메이션, 의미 없는 등장 효과)은 쓰지 않는다.
- `prefers-reduced-motion`을 존중한다: 애니메이션 대신 단계별 정지 화면으로 같은 정보를 준다.
- 모든 위젯은 키보드로 조작 가능하고, 텍스트 대안(현재 상태를 문장으로)을 제공한다.

### 2.4 성능 예산

- 본문은 **JS 없이** 읽힌다. 위젯·편집기는 화면에 보일 때 활성화한다.
- Pyodide는 첫 실행 버튼을 누를 때 내려받는다(로딩 진행 표시).
- 한 페이지의 위젯은 필요한 만큼만 — 위젯이 많을수록 좋은 장이 아니다.

## 3. 정보 구조

```
홈 ─ 로드맵 지도 (레이어 × 트랙 격자 + 장 단위 선수 지식 그래프)
 ├─ 학습 경로 (1–5단계, 배경별 경로, 도메인 트랙)
 ├─ 트랙 페이지: 핵심 질문 · 도달 목표 · 부 목록 · 졸업 과제 · 진행도
 │   └─ 부 → 장 → (절)
 ├─ 실습실: 내 코드 세션 · 제출 기록 · 실행 중인 작업
 ├─ 부록: 표기법 · 용어집 · 공식 · 치트시트 · 실패 사례 갤러리 · 템플릿 · 체크리스트
 └─ 검색 (한·영 용어 동시)
```

- **로드맵 지도:** 아래(L0)에서 위(L5)로 쌓인 레이어 격자에 트랙 카드가 놓이고, 트랙을 열면 장 단위 그래프가 펼쳐진다. 노드 색 = 진행 상태, 테두리 = 등급(필수·심화·참조). 장을 선택하면 그 장까지 가는 선수 경로가 강조된다.
- **사이드바:** 트랙 코드 배지(`MTH`, `PSI` …)와 트랙 색으로 구분, 등급 필터(필수만 / 필수+심화 / 전체).
- **역방향 링크:** "이 장을 선수로 하는 장"을 자동 생성한다.

│ 아핀 구조와 비선형성  Affine Structure and Nonlinearity            │

│ ┌ 학습 목표 ─────────────────────────┐ │  ...                    │

│ ┌ 코드 (브라우저 실행) ──────── ▶ 실행 ┐ │                        │
│ │ f = lambda x: A @ x + b              │ │                        │
│ │ f(np.zeros(2))   → array([0., 0.])   │ │                        │
│ └─────────────────────────────────────┘ │                        │
│ ┌ 실습 ── 연습문제 · 공개 테스트 3/3 ─┐ │                        │
│ ┌ 실패 사례 ⚠ ─────────────────────────┐│                        │

│ ┌ 통과 기준 ☐ ─────────────────────────┐│                        │

고정 제목 절(`학습 목표 · 실습 · 실패 사례 · 통과 기준`)과 `quiz.toml`은 빌드 시 전용 컴포넌트로 변환된다. 저자는 Markdown과 TOML만 쓴다.

## 5. 실습 화면

| 형태 | 화면 | 채점 |
|---|---|---|
| **코드 셀** (본문 안) | 편집 가능한 코드 + 실행 버튼 + 출력·그림. 원래 코드로 되돌리기 | 없음(탐색용) |
| **연습문제** | 문제 설명 · 시작 코드 · 공개 테스트 결과 · 힌트(단계적 공개) · 제출 | 공개 테스트는 즉시, 제출 시 비공개 테스트 |
| **터미널 실습** | 과제 체크리스트 + 웹 터미널. 체크 항목이 상태 검사로 자동 체크 | 상태 검사 스크립트 |
| **GPU 작업** | 제출 → 대기열 위치 → 실시간 로그·학습 곡선 → 결과 파일 | 결과 검증 스크립트 |
| **문서 산출물** | 템플릿을 채우는 편집기 → 리뷰 요청 | 루브릭 + 리뷰어 |

실행 계층(브라우저·CPU·GPU)은 코드 블록 머리에 배지로 표시해, 학습자가 "지금 무엇이 어디서 돌아가는지" 항상 안다 — 2.4장 "실행 위치의 지도"의 원칙을 서비스 자체에 적용한 것이다.

## 6. 퀴즈 화면

- 단일 선택 · 복수 선택 · 수치 입력. 수식이 들어간 선택지(KaTeX).
- 오답을 고르면 **그 선택지의 feedback**을 먼저 보여 주고 다시 시도하게 한다. 해설(`explanation`)은 정답 후 또는 포기 시 공개.
- 문항마다 연결된 학습 목표를 표시하고, 틀린 문항은 해당 절로 이동하는 링크를 준다.
- 연습 모드(무제한·즉시 채점)와 평가 모드(서버 채점·기록)를 구분한다.

## 7. 시각 디자인 방향

- **타이포그래피:** 본문 한글 산세리프(예: Pretendard), 코드 고정폭(예: JetBrains Mono, D2Coding), 수식 KaTeX. 줄간격 1.7–1.8, 본문 폭은 긴 글 읽기에 맞게 제한하고 위젯·코드는 본문보다 넓게 쓸 수 있게.
- **색:** 레이어는 명도로, 트랙은 색상으로 구분하는 절제된 팔레트. 의미 색(경고·정답·오답)은 트랙 색과 겹치지 않게. 라이트·다크 모두 대비 기준 충족.
- **위젯 시각 언어:** 모든 위젯이 같은 축·격자·색 토큰·컨트롤(재생 바, 슬라이더)을 쓴다. 위젯마다 디자인이 다르면 학습자가 매번 사용법을 배워야 한다.
- **그림:** SVG, 색은 토큰으로 지정해 라이트·다크 양쪽에서 읽히게.

## 8. 결정 기록

| 결정 | 이유 |
|---|---|
| 본문은 프레임워크 중립 Markdown + TOML로 `content/`에 둔다 | 집필과 플랫폼 개발을 분리하고, Git으로 리뷰·검증 |
| 이론과 실습을 함께 배우는 웹 서비스로 만든다 (프론트·API·DB·계산 서버) | 실행 가능한 코드, 자동 채점, 진도 공유가 필요 |
| 사이트는 Astro + React 아일랜드 (제안) | 정적 본문 + 선택적 인터랙티브 활성화, 위젯·편집기 자유도 |
| 브라우저 실행(Pyodide)을 1차 실행 계층으로 | 수학·확률·고전 ML 예제의 즉시성, 서버 비용 0 |
| 위젯은 `data/widgets.toml` 레지스트리로 관리 | 저자와 프론트 개발자의 공통 목록, 본문 참조 검증 |

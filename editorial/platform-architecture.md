# 플랫폼 아키텍처

> 상태: **설계 초안.** 이론과 실습을 함께 배우는 웹 서비스로서의 구조. UX는 [ux-design.md](ux-design.md), 콘텐츠 규칙은 [conventions.md](conventions.md).

## 1. 결론: 네 구성 요소는 모두 필요하다 — 역할 경계와 빠진 부품이 문제다

| 구성 요소 | 필요한가 | 맡는 것 | **맡지 않는 것** |
|---|---|---|---|
| 프론트엔드 | 필요 | 본문 렌더링, 위젯·모션, 코드 편집기, **브라우저 내 Python 실행**, 퀴즈 UI, 로드맵 지도 | 무거운 계산, 채점의 최종 판정 |
| 백엔드(API) | 필요 | 인증, 진도·퀴즈·제출 기록, 서버 채점, 계산 작업 접수·결과 전달, 지도교수용 현황 | **계산 자체**(계산 서버의 일), 책 본문 제공 |
| DB | 필요 | **사용자 상태만**: 계정·진도·퀴즈 응답·제출·작업 기록 | **책 본문**(Git이 원천) |
| 계산 서버 | 필요 | CPU·GPU 코드 실행, 자동 채점 테스트, 터미널 실습 환경 | 웹 요청 처리, 사용자 인증 |

**불필요하게 만들기 쉬운 것** — 피해야 할 것:

- **콘텐츠를 DB에 넣는 CMS 구조.** 본문·퀴즈·위젯 목록은 이 저장소(Git)가 원천이고 빌드 시 정적 파일로 만든다. 리뷰·버전 관리·`check` 검증을 그대로 유지할 수 있다. DB는 장을 영구 `id`(+ 콘텐츠 커밋 SHA)로만 참조한다.
- **모든 실행을 계산 서버로 보내는 구조.** 수학·확률·고전 ML 예제 대부분은 브라우저(Pyodide)에서 즉시 돌릴 수 있다. 계산 서버는 PyTorch·GPU·채점·터미널에만 쓴다.
- 초기의 마이크로서비스 분할, Kubernetes, 실시간 공동 편집. 처음에는 docker compose로 충분하다.

**빠진 부품** — 네 요소 외에 필요한 것:

| 부품 | 이유 | 후보 |
|---|---|---|
| 작업 큐 | 백엔드와 계산 서버를 분리하고, GPU 대기열·재시도·우선순위를 관리 | Redis (+ arq/RQ/Celery) |
| 객체 저장소 | 데이터셋, 실행 결과 파일, 그림, 체크포인트 | S3 호환(MinIO) |
| 인증 제공자 | 연구실·학교 계정 로그인 | OIDC(Google Workspace, GitHub 등) |
| 실시간 채널 | 실행 출력(stdout)·학습 곡선 스트리밍 | WebSocket 또는 SSE (백엔드 기능) |
| 관측 | 계산 서버 사용량·오류·남용 감지 | 구조화 로그 + 메트릭 |

## 2. 전체 구조

```
                         ┌──────────────── 빌드 (CI) ────────────────┐
  이 저장소 ──────────────▶ content/ · quiz.toml · widgets.toml → 정적 사이트 │
  (Git = 콘텐츠 원천)       │ labs/ lockfile → 실행 이미지(CPU/GPU)          │
                         └──────┬────────────────────────┬─────────────┘
                                │ 정적 파일(CDN)           │ 이미지 레지스트리
                                ▼                         ▼
┌──────────────── 브라우저 ────────────────┐       ┌────────── 계산 서버 ──────────┐
│ Astro 페이지 + React 아일랜드             │       │ runner (큐에서 작업을 가져감) │
│  · 위젯·모션 (페이지 상태 버스로 연결)     │       │  ├ CPU 샌드박스 컨테이너      │
│  · 코드 셀 / 편집기                       │       │  ├ GPU 샌드박스 컨테이너      │
│  · Pyodide (Web Worker)  ← T0 실행        │       │  └ 터미널 실습 컨테이너       │
│  · 퀴즈 · 진도                            │       │  (네트워크 차단·자원 제한)    │
└───────┬───────────────────────────────────┘       └──────▲───────────┬───────────┘
        │ HTTPS / WebSocket                                  │ pull       │ 결과·로그
        ▼                                                    │            ▼
┌──────────── 웹 서버 ─────────────┐   enqueue   ┌──────────┴──┐   ┌──────────────┐
│ API (FastAPI)                    │────────────▶│ Redis 큐     │   │ 객체 저장소   │
│  인증 · 진도 · 채점 · 작업 관리     │◀────────────│ (상태·이벤트) │   │ (MinIO/S3)   │
└───────┬──────────────────────────┘   events    └─────────────┘   └──────────────┘
        ▼
┌── PostgreSQL ──┐
│ 사용자 상태만    │
└────────────────┘
```

**계산 서버는 바깥에서 들어오는 연결을 받지 않는다.** runner가 큐에서 작업을 **가져가는(pull)** 구조이므로, 연구실 계산 서버에 공개 포트를 열 필요가 없다. 결과와 로그는 큐(이벤트)와 객체 저장소로 내보낸다.

## 3. 실행 계층

| 계층 | 위치 | 쓰는 곳 | 가능한 것 | 지연 | 비용 |
|---|---|---|---|---|---|
| **T0 브라우저** | Pyodide(WebAssembly), Web Worker | 수리 기초·확률·통계·고전 ML 예제, 위젯과 연동되는 코드 셀 | NumPy·SciPy·pandas·matplotlib·scikit-learn 등 Pyodide 패키지 | 즉시 (첫 로드에 수 초) | 서버 0 |
| **T1 CPU 샌드박스** | 계산 서버 | PyTorch CPU 예제, 자동 채점, 터미널 실습 | 실습 이미지 전체 | 수백 ms + 대기 | 낮음 |
| **T2 GPU 샌드박스** | 계산 서버 GPU | 학습 실습, profiling, 다중 GPU | CUDA 실습 이미지 | 대기열 | 높음 |

- 본문 코드 블록의 `exec` 속성(`browser`·`cpu`·`gpu`)이 계층을 정한다. [conventions.md §10](conventions.md)
- PyTorch는 브라우저에서 돌지 않으므로 딥러닝 장의 실행 코드는 T1 이상이다. 같은 개념을 NumPy로 먼저 보여 주고 T0로 돌리는 구성을 권장한다.
- **세션:** 같은 페이지에서 `session` 이름이 같은 코드 셀은 인터프리터 상태를 공유한다(T0는 Worker 하나, T1/T2는 컨테이너 안의 Jupyter 커널 하나).
- 실습 이미지는 `labs/`의 lockfile로 빌드한다 — **책의 실습 환경과 웹 실행 환경이 같다.**

## 4. 주요 흐름

| 상황 | 흐름 |
|---|---|
| 장 읽기 | CDN의 정적 HTML. JS 없이도 본문이 읽히고, 위젯·코드 셀은 화면에 보일 때 활성화 |
| 브라우저 코드 실행 | 편집기 → Web Worker(Pyodide) → 출력·그림을 페이지에 표시. `binds` 변수를 위젯과 주고받음 |
| 서버 코드 실행 | 편집기 → API(인증·한도 확인) → 큐 → runner → 샌드박스 → stdout을 WebSocket으로 스트리밍 → 결과 파일은 객체 저장소 |
| 퀴즈(연습) | 브라우저에서 즉시 채점·해설 표시. 로그인 상태면 응답을 API로 기록 |
| 퀴즈(평가) | 정답은 공개 번들에 넣지 않고 API가 채점 (빌드 시 공개용/정답용 데이터를 분리) |
| 코드 연습문제 | 공개 테스트는 화면에서, 제출 시 비공개 테스트를 T1에서 실행해 점수 기록 |
| 터미널 실습 | xterm.js ↔ WebSocket ↔ 실습 컨테이너. 종료 시 상태 검사 스크립트로 채점 |

## 5. 계산 서버 보안

계산 서버는 **신뢰할 수 없는 코드를 실행**한다. 연구실의 연구 데이터·계정과 섞이면 안 된다.

- 작업마다(또는 세션마다) 새 컨테이너. 강화된 런타임(gVisor 등), root 아님, 읽기 전용 이미지, 임시 작업 디렉터리
- **네트워크 차단**(필요한 실습만 허용 목록), 연구실 저장소·홈 디렉터리 마운트 금지
- CPU·메모리·프로세스 수·디스크·실행 시간 상한, 사용자별 일일 한도
- 서비스 전용 GPU 지정(`CUDA_VISIBLE_DEVICES`, 가능하면 MIG), 연구용 GPU와 분리
- 전용 시스템 계정으로 runner 실행, 모든 작업 기록(누가·언제·무엇을·얼마나)

## 6. 데이터 모델 (초안)

| 테이블 | 핵심 필드 |
|---|---|
| `users` | id, 이메일, 이름, 역할(학습자·조교·지도교수) |
| `cohorts` / `memberships` | 연구실·기수, 소속 |
| `progress` | user, `chapter_id`, `content_sha`, 상태(읽음·실습 완료·통과), 갱신 시각 |
| `quiz_attempts` | user, `chapter_id`, `question_id`, 응답, 정오, 시각 |
| `submissions` | user, `exercise_id`, 코드, 점수, `job_id` |
| `jobs` | id, user, 계층(T1/T2), 이미지, 상태, 시작·종료, 자원 사용량 |
| `sessions` | 커널 세션 id, user, 페이지, 만료 시각 |

`chapter_id`·`question_id`·`exercise_id`는 모두 저장소의 영구 id다. 장 번호나 파일 경로를 저장하지 않는다.

## 7. 기술 선택 (제안)

| 영역 | 제안 | 이유 |
|---|---|---|
| 사이트 | **Astro** + React 아일랜드 | 정적 본문은 빠르게, 인터랙티브 요소만 골라 활성화. Markdown 콘텐츠 처리 강함 |
| 수식 | KaTeX | 빠른 렌더링, 위젯 값과 연동한 동적 수식 |
| 편집기 | CodeMirror 6 | 가볍고 모바일 대응, 확장성 |
| 브라우저 실행 | Pyodide (Web Worker) | 과학 계산 패키지 지원, 서버 비용 0 |
| 시각화·모션 | D3(데이터 시각화), Motion(UI·전이 애니메이션), 필요 시 Three.js(3차원) | 역할별 최소 조합 |
| 터미널 | xterm.js | 표준 웹 터미널 |
| API | **FastAPI** + SQLAlchemy/Alembic | 연구실 공용 언어(Python), 계산 쪽 코드와 모델 공유 |
| DB | PostgreSQL | 관계형 사용자 상태, JSON 필드 |
| 큐 | Redis | 작업 큐 + 이벤트 스트림 |
| 실행 | 컨테이너 + Jupyter 커널(세션형) / 일회성 실행(채점형) | 상태 유지 실행과 채점을 모두 지원 |
| 배포 | 정적 사이트는 CDN, API·DB·Redis는 웹 서버(docker compose), runner는 계산 서버 | 계산 서버 노출 최소화 |

## 8. 저장소 구조 (모노레포 확장안)

```
content/  labs/  data/  editorial/  templates/  scripts/   ← 현재 (책)
apps/web/            프론트엔드 (Astro)
  src/widgets/<name>/  위젯 구현 (data/widgets.toml의 name과 일치)
services/api/        백엔드 (FastAPI)
services/runner/     계산 작업 워커 + 샌드박스 정책
images/              실행 이미지 정의 (lab-cpu, lab-gpu, lab-terminal)
infra/               docker compose(개발·배포), 환경 변수 예시
```

책 콘텐츠와 서비스 코드를 한 저장소에 두면 장 `id`·퀴즈·위젯 이름이 바뀔 때 프론트·채점기가 같은 커밋에서 함께 검증된다.

## 9. 단계별 구축

| 단계 | 범위 | 필요한 구성 요소 | 완료 기준 |
|---|---|---|---|
| **P1 정적 학습 사이트** | 본문·수식·사이드바·검색, 브라우저 코드 셀(T0), 퀴즈(클라이언트 채점), 위젯 3종, 진도(브라우저 저장) | 프론트만 | 7부·12부 일부 장을 끝까지 학습 가능 |
| **P2 계정과 진도** | 로그인, 진도·퀴즈 기록, 서버 채점 퀴즈, 지도교수 현황 | + API · DB | 연구실 기수 하나가 사용 |
| **P3 계산 서버 CPU** | 큐·runner, T1 실행, 코드 연습문제 자동 채점, 터미널 실습 | + 큐 · 계산 서버 · 객체 저장소 | MLC 실습 전체가 웹에서 실행 |
| **P4 GPU** | T2 실행, 사용자 한도·우선순위, 장시간 작업·대시보드 연결 | 계산 서버 GPU | MLS 실습(DDP·profiling) 실행 |
| **P5 출판** | PDF/인쇄 파이프라인 | 빌드 | 장별·전체 PDF |

P1은 백엔드·DB·계산 서버 **없이** 공개할 수 있다. 네 요소가 모두 필요하지만, 처음부터 모두 필요하지는 않다.

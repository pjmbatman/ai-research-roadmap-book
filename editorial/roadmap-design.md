# 로드맵 설계 근거

이 문서는 [OUTLINE.md](../OUTLINE.md)의 **트랙·레이어·평가 구조가 왜 이렇게 생겼는지** 기록한다.
트랙 정의의 원천은 [`book.toml`](../book.toml)이고, 아래 규칙 중 기계적으로 검사할 수 있는 것은 모두 `scripts/book.py check`가 검사한다.

## 1. 로드맵의 두 축

로드맵은 두 개의 서로 다른 질문에 답해야 한다.

| 축 | 질문 | 정하는 것 | 데이터 |
|---|---|---|---|
| **레이어 × 트랙** (구조) | 무엇이 무엇에 기대는가? | 트랙 사이의 의존 방향, 책의 부 순서 | `book.toml`의 `layers`·`tracks`, 장의 `prerequisites` |
| **단계** (경로) | 언제 무엇을 배우는가? | 개인의 학습 순서, 단계별 졸업 과제 | 학습 경로(0.3장), 종합 프로젝트(26.5장) |

두 축을 섞지 않는 것이 핵심이다. 수학(L1)은 딥러닝(L2)보다 **아래 레이어**지만, 학습자는 나선형 경로를 따라 **1단계에서 딥러닝 학습 루프를 먼저 얕게 경험**하고 2단계에서 그 수학을 깊이 배운다.
레이어는 "깊이 이해하려면 무엇이 먼저 필요한가"이고, 단계는 "언제 처음 만나는가"다.

## 2. 레이어와 트랙

```
L5 조직   │ LAB 연구실 운영
──────────┼──────────────────────────────────────────────────────────
L4 연구   │ RES 연구 방법론          SCI 과학·공학 AI
──────────┼──────────────────────────────────────────────────────────
L3 확장   │ MLA 머신러닝 심화        MLS 머신러닝 시스템
──────────┼──────────────────────────────────────────────────────────
L2 핵심   │ MLC 머신러닝 핵심
──────────┼──────────────────────────────────────────────────────────
L1 기반   │ INF 연구 인프라  RSE 연구 소프트웨어 공학  MTH 수리 기초  PSI 확률·통계적 추론
──────────┼──────────────────────────────────────────────────────────
L0 입문   │ ORI 오리엔테이션
          │                                                REF 참고 자료 (레이어 밖)
```

| 레이어 | 의미 | 트랙 |
|---|---|---|
| **L0 입문** | 어떤 선수 지식도 요구하지 않는 출발점 | `ORI` |
| **L1 기반** | 서로 병행해 배우는 네 기반 역량. 다른 기반 트랙에만 기댄다 | `INF` `RSE` `MTH` `PSI` |
| **L2 핵심** | 기반을 결합해 학습 시스템 전체를 다루는 역량 | `MLC` |
| **L3 확장** | 핵심 위에서 모델링의 **폭**(MLA)과 실험의 **규모**(MLS)를 넓힌다 | `MLA` `MLS` |
| **L4 연구** | 모든 역량을 연구 질문(RES)과 도메인 문제(SCI)에 통합한다 | `RES` `SCI` |
| **L5 조직** | 개인 역량을 연구실의 지속 가능한 자산으로 전환한다 | `LAB` |

### 2.1 기반 레이어가 네 트랙인 이유

책의 네 축(이론·구현·연구·운영) 중 연구를 뺀 세 축이 기반에서 갈라진다.

| 축 | 기반 트랙 | 구분의 근거 |
|---|---|---|
| 운영 | `INF` 연구 인프라 | 대상이 **실행 환경**(서버·드라이버·패키지·컨테이너·Git). 평가가 터미널 상태 검사로 이루어진다 |
| 구현 | `RSE` 연구 소프트웨어 공학 | 대상이 **코드 자체**(언어·구조·설정·테스트). 평가가 코드 리뷰와 테스트로 이루어진다 |
| 이론 | `MTH` 수리 기초 | **결정론적 계산의 수학**: 공간(선형대수)·변화(미적분)·근사(수치해석)·최적화 |
| 이론 | `PSI` 확률·통계적 추론 | **불확실성의 수학**: 확률·추정·베이지안·정보와 일반화 |

수학을 두 트랙으로 나눈 이유는 분량(53장)만이 아니다. MTH와 PSI는 사고방식이 다르고(계산 vs 추론), 선수 관계도 한 방향이다(PSI → MTH, 반대 방향 없음). 최적화는 미적분에만 기대므로 MTH에 속한다.

### 2.2 확장 레이어가 두 트랙인 이유

`MLA`(생성모델·강화학습·신뢰성)는 **무엇을 모델링하는가**를 넓히고, `MLS`(실험 추적·재현성·profiling·분산학습)는 **얼마나 크고 믿을 수 있게 돌리는가**를 넓힌다. 둘 다 MLC 위에 있지만 서로 기대지 않는다.

### 2.3 근거: 실제 선수 지식 그래프

레이어는 선언이 아니라 **190개 장의 `prerequisites`에서 집계한 트랙 간 의존**과 일치해야 한다. 집계 결과는 OUTLINE.md의 "트랙 간 의존" 표에 자동으로 생성되며, 다음 두 규칙을 `check`가 강제한다.

1. **레이어 단조성:** 모든 장의 선수 지식은 같은 레이어 또는 더 낮은 레이어의 트랙에 있다.
2. **트랙 비순환:** 트랙 단위로 집계한 의존 그래프에 순환이 없다(같은 레이어 안에서도).

이 두 규칙 덕분에 로드맵은 항상 아래에서 위로 읽히고, 책의 부 순서(트랙 순서 = 레이어 순서)도 같은 방향을 따른다. 장을 추가하거나 선수 지식을 바꿨을 때 이 규칙이 깨지면 **트랙 배치가 틀렸거나 선수 지식이 틀린 것**이다.

## 3. 트랙 이름 규칙

| 요소 | 규칙 | 예 |
|---|---|---|
| `key` | 영어 kebab-case. frontmatter `track` 값이자 URL 경로. 바꾸지 않는다 | `research-software-engineering` |
| `code` | 영문 대문자 3자. UI 배지·짧은 참조. 영어 이름의 머리글자에서 따온다 | `RSE` |
| `name` | 한국어 **분야명**(명사구). "~하기", "~의 기초" 같은 서술형을 쓰지 않는다 | 연구 소프트웨어 공학 |
| `name_en` | 학계·산업에서 **실제로 통용되는 분야명**. 새로 만들지 않는다 | Research Software Engineering |
| `question` | 트랙이 답하는 핵심 질문 하나 | 수식과 아이디어를 어떻게 정확하고 유지 가능한 코드로 옮기는가? |
| `outcome` | "~한다"로 끝나는 도달 목표. 관찰 가능한 행동 | 설정·CLI·테스트·문서를 갖춘 연구 프로젝트를 만들고 협업한다 |

계층을 나타내는 말은 머신러닝 트랙에만 일관되게 쓴다: **핵심**(Core) → **심화**(Advanced) → **시스템**(Systems).
`Research Software Engineering`, `Machine Learning Systems`, `Probabilistic and Statistical Inference`, `Scientific Machine Learning`은 모두 해당 분야에서 쓰는 이름이다.

## 4. 평가 체계

트랙마다 **주된 평가 방식**이 다르다. 실습이 코드가 아닌 트랙(오리엔테이션·연구 방법론·수학 일부)은 개념 퀴즈와 문서 산출물로 통과를 확인한다.

| 평가 방식 | 수단 | 채점 | 주로 쓰는 트랙 |
|---|---|---|---|
| `quiz` 개념 퀴즈 | 장의 `quiz.toml` — 단일 선택·복수 선택·수치 입력 | 자동 | ORI · MTH · PSI · RES (+ 모든 트랙 보조) |
| `code` 코드 실습 | 브라우저 또는 계산 서버에서 실행, 공개·비공개 테스트 | 자동 | RSE · MTH · PSI · MLC · MLA · MLS · SCI |
| `terminal` 터미널 실습 | 격리된 Linux 환경에서 명령 수행, 상태 검사 스크립트 | 자동 | INF · MLS |
| `document` 문서 산출물 | 문제 정의서·실험 계획서·재현 보고서 템플릿 | 루브릭 + 리뷰 | ORI · RES · SCI · LAB |
| `review` 동료·지도 리뷰 | 코드·실험·발표 리뷰 | 사람 | RSE · RES · LAB |

### 4.1 퀴즈를 쓰는 원칙

- 모든 문항은 장의 **학습 목표 하나**에 연결된다(`objective`). 학습 목표와 무관한 지식 확인 문항은 쓰지 않는다.
- 암기가 아니라 **오개념을 드러내는** 문항을 쓴다. 오답 선택지는 실제로 자주 하는 착각이어야 하고, 각 오답에 `feedback`을 단다.
- 모든 문항에 `explanation`(왜 정답인가)을 쓴다. 퀴즈는 시험이 아니라 학습 도구다.
- 수치 입력 문항은 손으로 계산 가능한 크기로 낸다.
- 본문 중간에 `::quiz{id="..."}`로 한 문항을 삽입해 **예측해 보기**(읽기 전에 답하고, 위젯·코드로 확인)에 쓴다.

### 4.2 트랙 졸업 과제

트랙마다 `capstone`이 있다(OUTLINE.md 트랙 머리 참고). 트랙의 모든 필수 장 통과 기준 + 졸업 과제 = 트랙 이수.
26.5장의 단계별 종합 프로젝트(A–H)는 **여러 트랙을 가로지르는** 과제이고, 트랙 졸업 과제는 **한 트랙 안의** 과제다.

## 5. 초안(ChatGPT 답변)에서 바꾼 것

출발점이었던 "20개 대분류·80개 장" 초안의 좋은 점 — 네 축 병행, 장의 공통 형식, 필수·심화·참조, 목차 순서와 학습 순서의 분리, 산출물 기반 진도 — 은 그대로 가져왔다. 바꾼 것은 다음과 같다.

1. **트랙·레이어 도입.** 평평한 20개 부 대신, 검증 가능한 의존 규칙을 가진 6개 레이어·11개 트랙(+참고).
2. **작업대를 앞으로.** 신입 연구원이 첫 주에 막히는 곳은 수학이 아니라 서버와 환경이다. INF·RSE를 L1에 두고 부 번호도 앞에 배치했다.
3. **첫 파이프라인 장(1.4)** — 나선형 학습의 진입점.
4. **요청 주제를 독립 장으로:** 아핀 구조와 비선형성(7.2), rank(7.3), 다양체(7.8), 분포 기반 문제 정의(12.3), 학습 루프 해부(17.5), Ubuntu·CUDA(3.2), venv·uv·conda(3.3), 에이전트 지침(4.4), MCP(4.5), 실행 위치의 지도(2.4), 프로젝트 구조(6.1), 설정 관리(6.3), CLI(6.4), 대시보드(17.8).
5. **보강:** 텐서와 einsum(7.7), 함수공간(7.9), 2차 최적화(10.5), 베이지안 최적화(10.7), 다변량 가우시안(11.4), 확률과정·SDE(11.7), Gaussian process(13.7), 스케일링 법칙(14.5), LLM 기초(18.5), flow matching(19.6), 강화학습 부(20부), conformal prediction(21.3), GPU 메모리(22.5), 연구 방법론 4장 → 12장.
6. **수치해석을 독립 부로**(9부) — 공학 연구에서 solver는 데이터 생성기이자 baseline이자 오차의 원천이다.

## 6. 유지할 원칙

1. **한 장 = 한 학습 단위.** 장이 두 목표를 가지면 나눈다.
2. **모든 장은 산출물로 끝난다.** 통과 기준이 "이해한다"로 끝나면 다시 쓴다.
3. **선수 지식은 최소로.** 꼭 필요한 직전 장만 적는다. 단, 트랙을 넘는 의존은 빠뜨리지 않는다 — 로드맵의 근거가 되기 때문이다.
4. **필수(core)는 모든 연구원이 직접 할 수 있어야 하는 것만.** 현재 190장 중 139장 — 집필하며 심화로 내릴 후보를 검토한다.
5. **도구는 개념과 절차로 가르치고, 버전·화면은 갱신되는 참조로 둔다.**

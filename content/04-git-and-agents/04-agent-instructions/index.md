# 에이전트 지침: AGENTS.md·CLAUDE.md·SKILL.md

새로 들어온 대학원생에게 연구실 저장소를 맡기면 첫 주에 같은 질문을 한다. 환경은 어떻게 만드는가, 테스트는 무엇으로 돌리는가, 건드리면 안 되는 데이터는 어디 있는가, 결과는 어디에 기록하는가. 선배가 한 번 답해 주면 그 학생은 기억한다. AI 코딩 에이전트는 그렇지 않다. 세션이 끝나면 잊고, 다음 세션에서 같은 것을 다시 추측한다. 추측은 틀리기도 한다. 테스트 명령을 잘못 짐작해 "테스트 없음"으로 넘어가거나, 원본 데이터 파일을 고치거나, 쓰지 말아야 할 패키지를 설치한다.

에이전트 지침 파일은 이 문제를 푼다. 프로젝트 저장소에 "에이전트를 위한 README"를 두면, 지침을 읽는 도구는 세션을 시작할 때마다 그것을 맥락으로 읽는다. 이 장은 지침 파일의 역할과 범위, 무엇을 쓰고 무엇을 쓰지 않을지, 반복 절차를 skill로 묶는 법, 그리고 지침을 코드처럼 관리하는 법을 다룬다. 예시는 이 책의 저장소 자체다. 이 책은 사람과 AI 에이전트가 함께 쓰고 있고, 그 규칙이 `AGENTS.md`, `CLAUDE.md`, `.claude/skills/`에 들어 있다.

## 학습 목표

- 프로젝트 지침 파일의 역할과 적용 범위를 안다
- 재사용 가능한 skill을 작성한다
- 지침을 버전 관리한다

## 프로젝트 지침 파일

**정의.** 프로젝트 지침 파일은 코딩 에이전트가 그 프로젝트에서 작업할 때 읽도록 저장소에 두는 Markdown 파일이다. 특별한 문법은 없다. 에이전트는 이 텍스트를 작업의 맥락으로 받아들인다.

**파일 이름.** 도구마다 읽는 이름이 다르다. `AGENTS.md`는 여러 코딩 에이전트가 공통으로 읽도록 제안된 열린 형식으로, 스스로를 "에이전트를 위한 README"라고 소개한다. 필수 항목은 없고 보통의 Markdown이다. 일부 도구는 자기 이름이 붙은 파일을 읽는다. 예를 들어 Claude Code는 `CLAUDE.md`를 읽는다. 여러 도구를 함께 쓰는 프로젝트에서 같은 규칙을 파일마다 복사하면 언젠가 어긋난다. 이 책의 저장소는 규칙의 원천을 `AGENTS.md` 하나로 두고, `CLAUDE.md`에는 한 줄만 쓴다.

```markdown
@AGENTS.md
```

`@경로`는 그 파일의 내용을 불러오라는 표기로, 이 저장소의 `editorial/workflow.md`도 "`CLAUDE.md`는 `@AGENTS.md`로 같은 규칙을 불러온다"고 설명한다. 이런 불러오기 문법이 있는지, 없으면 symbolic link나 짧은 안내 문장으로 대신해야 하는지는 도구마다 다르다.

**전역·프로젝트·디렉터리 수준.** 많은 도구가 지침을 여러 수준에 둘 수 있게 한다.

| 수준 | 예 | 담는 것 | 공유 |
|---|---|---|---|
| 사용자 전역 | 홈 디렉터리의 도구 설정 폴더 | 개인의 작업 습관(응답 언어, 선호하는 도구) | 나만 |
| 프로젝트 | 저장소 루트의 `AGENTS.md` | 프로젝트 전체의 구조·명령·규칙 | commit해 팀 전체 |
| 디렉터리 | `services/sim/AGENTS.md` | 하위 프로젝트에만 해당하는 명령·규칙 | commit해 팀 전체 |

여러 수준의 지침이 충돌할 때의 규칙도 도구마다 다르다. `AGENTS.md` 형식이 제안하는 관례는 "**고치는 파일에 가장 가까운 `AGENTS.md`가 우선하고, 사용자가 대화에서 명시한 지시가 모든 것에 우선한다**"이다. 그래서 여러 하위 프로젝트가 있는 저장소(monorepo)에서는 루트에 공통 규칙을, 각 하위 디렉터리에 그 부분의 빌드·테스트 명령을 둔다.

::quiz{id="nearest-agents-md"}

**확인 절차.** 쓰는 도구가 어떤 파일을 읽는지는 다음 순서로 확인한다(도구와 버전에 따라 바뀌므로 이 책은 구체적인 목록을 싣지 않는다).

1. 도구의 공식 문서에서 지침 파일(memory, rules, instructions 등으로 부른다)의 **이름, 위치, 여러 파일을 합치는 규칙**을 찾는다.
2. 새 세션에서 에이전트에게 "지금 읽은 지침 파일과 그 핵심 규칙"을 요약하게 해, 의도한 파일이 실제로 읽혔는지 본다.
3. 지침에 일부러 확인용 규칙(예: "작업을 마칠 때 사용한 테스트 명령을 보고한다")을 넣고 그 규칙이 지켜지는지 본다.

**지침은 권한이 아니다.** 지침 파일에서 가장 흔한 오해다. 지침은 에이전트가 **읽고 따르려고 하는** 텍스트이지, 행동을 막는 장치가 아니다. 대부분의 경우 지켜지지만, 긴 작업 중에 다른 맥락에 밀리거나, 규칙을 다르게 해석하거나, 외부 문서에 들어 있던 지시에 휘둘릴 수 있다(4.5장). 그래서 "절대 일어나면 안 되는 일"은 층을 나눠 막는다.

| 층 | 무엇이 | 이 책 저장소의 예 |
|---|---|---|
| 지침 | 에이전트가 무엇을 해야 하고 하지 말아야 하는지 **알게** 한다 | `AGENTS.md`의 "반드시 지킬 것" |
| 절차 | 반복 작업을 **같은 방식으로** 하게 한다 | `.claude/skills/write-chapter/SKILL.md` |
| 권한 | 어떤 행동을 승인 없이 **허용**할지 정한다 | `.claude/settings.json`의 사전 허용 명령 목록 |
| 검사 | 결과가 규칙을 지켰는지 **기계적으로 확인**한다 | `python3 scripts/book.py check`, CI |
| 보호 | 되돌리기 어려운 행동을 **원천 차단**한다 | branch 보호, 범위가 제한된 자격 증명 |

이 저장소의 `.claude/settings.json`은 `python3 scripts/book.py check` 같은 검증 명령만 승인 없이 실행하도록 허용한다. 지침이 "변경 후 check를 실행한다"고 말하고, 권한 설정이 그 명령을 마찰 없이 실행하게 하고, check 스크립트가 규칙 위반을 잡는다. 세 층이 같은 규칙을 다른 방식으로 받친다.

::quiz{id="instructions-are-not-permissions"}

## 무엇을 쓰는가

**원칙.** 지침에는 **에이전트가 매번 필요로 하지만 코드만 읽어서는 알기 어려운 것**을 쓴다. 반대로 코드에서 바로 읽히는 것(함수가 무엇을 하는지), 가끔만 필요한 긴 설명(이론 배경), 그리고 비밀값은 쓰지 않는다.

**프로젝트 구조.** 디렉터리마다 무엇이 있는지 한두 줄로. 특히 "어디에 무엇을 두는가"의 규칙. 이 책의 `AGENTS.md`는 "이 저장소는 코드 프로젝트가 아니라 **책**이다"로 시작해, 에이전트가 저장소를 소프트웨어로 오해하지 않게 한다. 그다음 먼저 읽을 문서 네 개를 순서대로 가리킨다. 긴 규칙을 지침에 다 쓰지 않고, 원천 문서를 가리키는 방식이다.

**설치·실행·테스트 명령.** 지침에서 가장 쓸모 있는 부분이다. 그대로 복사해 실행할 수 있는 정확한 명령을 쓴다. "테스트를 돌린다"가 아니라 `python -m pytest -q tests`. 그리고 **작업이 끝났다는 기준**이 되는 명령을 명시한다. 이 저장소의 지침은 "변경 후 `python3 scripts/book.py check`를 실행하고 통과시킨다"고 쓴다. 이 한 줄이 있으면 에이전트는 작업을 마치기 전에 스스로 검사하고, 사람은 보고에서 그 결과를 확인할 수 있다.

**금지사항.** 하지 말아야 할 일을 구체적으로. "조심한다"가 아니라 "`OUTLINE.md`는 직접 수정하지 않는다(생성 파일이다)", "장 `id`를 바꾸지 않는다(사용자 진도 기록의 키다)". 이유를 함께 쓰면 에이전트가 규칙이 적용되는 범위를 더 정확히 판단한다. 비슷한 상황에서 규칙의 취지를 따를 수 있기 때문이다.

**검증 기준.** 작업 결과를 어떻게 확인하는가. 이 저장소에서는 "실습 코드는 실제로 실행해 본 결과만 본문에 쓴다", "존재를 직접 확인하지 않은 논문·API·수치를 쓰지 않는다"가 그렇다. 연구 프로젝트라면 "새 실험은 seed 3개로 돌리고 평균과 표준편차를 보고한다", "test split의 결과는 최종 보고 전에는 보지 않는다" 같은 규칙이 여기 들어간다.

**데이터 취급 규칙.** 연구 프로젝트에서 특히 중요하다. 원본 데이터는 읽기 전용, 개인정보·공개 전 데이터는 외부 서비스로 보내지 않음, 데이터의 위치와 접근 방법, 용량이 큰 파일을 열 때의 주의.

::quiz{id="what-goes-in-agents-md"}

**길이.** 지침은 짧을수록 잘 지켜진다. 규칙이 백 개면 어느 것이 중요한지 에이전트도 사람도 모른다. 이 책의 `AGENTS.md`는 39줄이다. 길어지면 다음을 시도한다.

- 기계적으로 확인할 수 있는 규칙은 지침에서 빼고 **검사 스크립트**로 옮긴다. 이 저장소의 frontmatter 형식, 고정 절 제목, 선수 지식의 레이어 규칙은 `book.py check`가 검사하므로 지침에는 "check를 통과시킨다" 한 줄이면 된다.
- 특정 작업에만 필요한 절차는 **skill**로 옮긴다(다음 절).
- 하위 디렉터리에만 해당하는 규칙은 그 디렉터리의 지침 파일로 옮긴다.

:::note[분야 예시]
여러 기관이 공유하는 기후 모델 후처리 저장소라면 지침에 이런 규칙이 들어간다. "모델 출력은 `/shared/cmip/` 아래에 있고 읽기 전용이다. 변수 이름은 CF 규약을 따른다. 온도는 켈빈으로 저장되어 있으니 변환은 그림을 그리는 단계에서만 한다. 새 지표를 추가하면 `tests/test_metrics.py`에 알려진 답이 있는 작은 격자 예시를 함께 추가한다." 단위와 데이터 위치처럼, 코드를 읽어서는 확신할 수 없지만 틀리면 결과 전체가 틀리는 정보가 지침의 핵심이다.
:::

## Skill

**왜 필요한가.** 지침 파일은 **항상** 맥락에 들어간다. 그래서 가끔 하는 작업의 상세 절차까지 넣으면 지침이 길어지고, 핵심 규칙이 묻힌다. 반복 작업의 절차는 따로 묶어 두고, 그 작업을 할 때만 꺼내 쓰는 편이 낫다. 이것이 skill이다.

**정의.** skill은 반복 작업 하나의 절차를 담은 폴더다. 형식은 Agent Skills 명세로 공개되어 있다. 폴더 안의 `SKILL.md`는 YAML frontmatter와 본문으로 이루어진다. frontmatter의 필수 항목은 두 개다.

- `name` — skill의 이름. 소문자·숫자·하이픈만 쓰고, 폴더 이름과 같아야 한다.
- `description` — 이 skill이 **무엇을 하는지**와 **언제 쓰는지**

본문에는 절차, 확인할 것, 예시를 쓴다. 이 책 저장소의 skill 하나를 보면 구조가 보인다.

```markdown
---
name: add-quiz
description: 장의 학습 목표에 맞는 개념 퀴즈 문항을 quiz.toml에 추가한다. 사용자가 퀴즈·객관식 문제·문제집 작성을 요청할 때 사용한다.
---

# 퀴즈 문항 추가

## 준비
1. 장 파일의 `## 학습 목표`를 읽고 번호를 매긴다(1부터).
...
## 검증
- **모든 정답을 직접 풀어서 확인한다.** 계산 문항은 코드로 확인한다.
...
```

**description과 트리거.** 명세는 skill을 **단계적으로**(progressive disclosure) 읽는 구조를 설명한다. 에이전트는 시작할 때 모든 skill의 `name`과 `description`만 맥락에 두고, 지금 작업에 어떤 skill이 필요하다고 판단하면 그때 그 `SKILL.md` 본문 전체를 읽고, 본문이 가리키는 보조 파일은 필요할 때만 연다. 그래서 description은 에이전트가 "이 요청에 이 skill을 써야 하는가"를 판단하는 유일한 근거다. 무엇을 하는지만 쓰지 말고 **어떤 요청·상황에서 쓰는지**를 구체적으로 쓴다. 사용자가 쓸 법한 표현("퀴즈", "객관식 문제", "문제집")을 넣는 것도 도움이 된다. 이 저장소의 skill은 사용자가 이름으로 직접 부를 수도 있다(`/write-chapter`처럼). skill의 위치(이 저장소는 `.claude/skills/<이름>/SKILL.md`)와 호출 방법은 도구마다 다르므로 도구 문서에서 확인한다.

::quiz{id="skill-description"}

**보조 스크립트.** skill 폴더에는 `SKILL.md` 외에 스크립트, 템플릿, 참고 문서를 함께 둘 수 있다. 명세는 이를 `scripts/`, `references/`, `assets/` 폴더로 정리하기를 권하고, 본문은 짧게(500줄 이내) 유지하고 긴 참고 자료는 별도 파일로 옮기라고 권한다. 본문에서 "형식 검사는 `scripts/validate.py`를 실행한다"처럼 가리키면, 에이전트는 필요할 때 그 파일을 읽거나 실행한다. 정해진 계산이나 형식 변환은 자연어 절차보다 스크립트가 훨씬 안정적이다. 매번 같은 결과를 내고, 맥락을 차지하지 않기 때문이다.

**좋은 skill의 조건.**

- **한 가지 일을 한다.** "퀴즈 추가"와 "장 리뷰"는 다른 skill이다. 이 저장소의 세 skill(`write-chapter`, `review-chapter`, `add-quiz`)이 그렇게 나뉘어 있다.
- **끝나는 조건이 있다.** 어떤 검사를 통과하면 끝인지, 무엇을 보고하는지를 쓴다. `write-chapter`는 "status를 draft로 바꾼다, check를 실행한다, 쓴 절·실습·확인 필요 목록을 보고한다"로 끝난다.
- **하지 말아야 할 일을 쓴다.** `review-chapter`는 description부터 "파일은 고치지 않는다"고 쓴다. 리뷰와 수정을 섞지 않기 위해서다.
- **사람에게 넘길 지점을 쓴다.** 판단이 필요한 곳(단위가 없으면 묻는다, 허용 오차가 애매하면 확인받는다)에서 멈추게 한다.

## 지침의 유지보수

**지침도 코드다.** 지침은 저장소에 commit하고, 바꿀 때는 PR로 리뷰를 받는다. 지침 한 줄이 이후 모든 에이전트 작업의 방식을 바꾸기 때문이다. 코드와 지침을 함께 바꾸는 변경(명령 이름 변경, 디렉터리 이동)이라면 **같은 PR**에서 고친다. 이 저장소의 `AGENTS.md`도 "목차 구조를 바꿨다면 `python3 scripts/book.py outline`으로 `OUTLINE.md`를 재생성한다"처럼 코드 변경과 함께 해야 할 일을 적어 둔다.

**지침과 실제 코드의 불일치.** 가장 흔한 고장은 지침에 적힌 명령이 더는 동작하지 않는 것이다. 스크립트 이름이 바뀌었거나, 옵션이 없어졌거나, 디렉터리가 옮겨졌다. 에이전트는 실패한 명령을 보고 다른 방법을 추측하거나, 실패를 무시하고 진행하거나, 옛 스크립트를 다시 만든다. 이 불일치는 사람이 읽어서는 잘 보이지 않으므로 **기계적으로 검사**한다. 이 장의 실습 폴더에 있는 `check_instructions.py`는 다음을 한다.

- `AGENTS.md`와 각 `SKILL.md`의 ```` ```bash ```` 블록에 적힌 명령을 프로젝트 디렉터리에서 **실제로 실행**해 실패를 보고한다.
- `AGENTS.md`가 가리키는 상대 경로가 실제로 있는지 본다.
- `SKILL.md` frontmatter의 `name` 형식, 폴더 이름과의 일치, `description`의 길이를 검사한다.

이런 검사를 CI에 넣으면 지침이 코드와 함께 낡는 것을 막을 수 있다.

::quiz{id="stale-instructions"}

**오래된 지침 정리.** 지침은 늘어나기만 하는 경향이 있다. 사고가 한 번 날 때마다 규칙이 하나씩 더해진다. 주기적으로(예: 큰 작업 단위가 끝날 때) 다음을 확인한다.

- 이 규칙이 아직 필요한가? 원인이 된 코드가 없어졌거나 검사 스크립트가 대신하게 되었으면 지운다.
- 두 규칙이 서로 모순되지 않는가?
- 이 규칙이 지침 파일에 있어야 하는가, skill이나 하위 디렉터리 지침으로 옮길 수 있는가?

**에이전트의 실수에서 배운다.** 에이전트가 같은 실수를 두 번 하면 지침이 부족하다는 신호다. 다만 실수마다 규칙을 하나씩 더하기 전에, 그 실수를 **검사로 막을 수 있는지** 먼저 본다. 검사는 지침보다 확실하다.

## 실습

새 에이전트가 프로젝트를 탐색하고 최소 실험을 실행할 수 있는 `AGENTS.md`와, 반복 작업 하나에 대한 `SKILL.md`를 작성한다.

**1. 예시를 읽는다.** `labs/git-and-agents/agent-instructions/sample_project/`는 방사성 붕괴 계수 자료에서 반감기를 추정하는 최소 연구 프로젝트다. `AGENTS.md`(명령·규칙·반복 작업 안내)와 `skills/add-decay-dataset/SKILL.md`(새 테스트 조건을 추가하는 절차)가 들어 있다. 점검 스크립트로 확인한다.

```bash
# 집필 시점 예시 — 저장소 루트에서 실행
uv run --project labs python labs/git-and-agents/agent-instructions/check_instructions.py \
    labs/git-and-agents/agent-instructions/sample_project
```

집필 시점에는 "통과"를 출력했다. 같은 폴더의 `test_check_instructions.py`는 지침의 명령을 옛 이름으로 바꾸거나 skill 폴더를 지운 사본에서 이 점검이 실패하는지 확인한다.

**2. 자신의 프로젝트에 쓴다.** 자신의 연구 저장소(없으면 4.2장 실습의 연습 저장소)에 다음을 만든다.

- `AGENTS.md`: 프로젝트 한 줄 소개, 디렉터리 구조, 환경 설치 명령, 테스트 명령, **1분 안에 끝나는 smoke test 명령**, 금지사항(원본 데이터, test split, 의존성 추가), 데이터 취급 규칙. 50줄 이내를 목표로 한다.
- `SKILL.md` 하나: 그 프로젝트에서 반복하는 작업 하나(새 실험 설정 추가, 결과 표 갱신, 새 데이터셋 등록 등). description에 무엇을·언제를 쓰고, 본문은 끝나는 조건과 보고 형식으로 끝낸다.
- 사용하는 도구가 다른 파일 이름을 읽는다면 그 파일에서 `AGENTS.md`를 불러오게 한다(불러오기 문법이 있는지 도구 문서에서 확인한다).

`check_instructions.py`를 자신의 프로젝트에 실행해 통과시킨다. 이 스크립트는 `skills/*/SKILL.md` 위치를 가정하므로, 다른 위치를 쓰면 스크립트의 경로를 고친다.

**3. 처음 보는 에이전트로 시험한다.** 지침의 최종 시험은 사람이 아니라 처음 보는 에이전트다. 이전 대화가 없는 새 세션을 열고 다음만 요청한다.

```
이 저장소의 지침을 읽고, 환경을 준비한 뒤 smoke test를 실행해 결과를 보고해 줘.
지침에 없는 것을 추측해야 했다면 무엇을 추측했는지도 알려 줘.
```

에이전트가 추측했다고 보고한 부분, 실패한 명령, 지침을 어긴 행동을 기록하고 지침을 고친다. 추측 없이 smoke test를 통과할 때까지 반복한다. 마지막으로 skill에 해당하는 작업을 요청해, 이름을 말하지 않아도 그 skill이 쓰이는지 확인한다.

## 실패 사례

- **지침을 너무 길게 써서 핵심 규칙이 묻히는 것.** 사고가 날 때마다 규칙을 더하다 보면 지침이 수백 줄이 되고, 정말 중요한 "원본 데이터는 수정하지 않는다"가 코딩 스타일 규칙 사이에 묻힌다. 검사로 대신할 수 있는 규칙은 검사로, 특정 작업의 절차는 skill로 옮기고, 지침에는 매번 필요한 것만 남긴다.
- **실제와 다른 명령이 지침에 남아 있는 것.** 스크립트 이름을 바꾸고 지침을 고치지 않으면, 에이전트는 실패한 명령을 우회하는 방법을 스스로 찾는다. 그 우회가 테스트를 건너뛰는 것일 수도 있다. 명령을 바꾸는 PR에서 지침을 함께 고치고, 지침의 명령을 실행해 보는 검사를 CI에 둔다.
- **지침을 권한으로 착각하는 것.** "push하지 않는다"를 지침에 썼으니 안전하다고 생각하고 push 권한이 있는 토큰을 에이전트 환경에 둔다. 되돌리기 어려운 행동은 권한 설정과 저장소 보호로 막는다.
- **비밀값이나 개인 경로를 지침에 쓰는 것.** 지침 파일은 commit되어 공유되고, 모델의 맥락에 그대로 들어간다. API key 값 대신 환경변수 이름을, `/home/내이름/data` 대신 프로젝트 기준 상대 경로나 설정 변수를 쓴다.

## 통과 기준

- 자신의 프로젝트에 `AGENTS.md`와 `SKILL.md` 하나를 commit하고, `check_instructions.py`(또는 같은 일을 하는 자신의 검사)를 통과시킨다.
- 이전 대화가 없는 새 에이전트 세션이 지침만으로 환경을 준비하고 smoke test를 통과한다. 에이전트가 추측했다고 보고한 항목이 없거나, 있으면 그것을 지침에 반영한 뒤 다시 통과한 기록을 남긴다.
- 지침 층(지침·절차·권한·검사·보호) 중 자신의 프로젝트에서 각 금지사항을 어느 층에서 막는지 표로 정리한다.

# 연구 윤리와 오픈 사이언스

연구 윤리는 "나쁜 사람이 하는 나쁜 일"을 막는 규칙으로만 여겨지기 쉽다. 실제로 연구자를 곤란하게 만드는 것은 대부분 악의가 아니라 **관행과 무지**다. seed 다섯 개 중 가장 좋은 것을 보고하는 습관, 웹에서 내려받을 수 있으니 써도 된다는 생각, 연구실 관행이라며 저자 목록에 이름을 올리는 일, AI 도구로 쓴 문단을 아무 표시 없이 제출하는 일, 라이선스 없이 코드를 공개하는 일. 하나하나는 사소해 보이지만, 논문 철회·데이터 삭제 요청·공동 연구 파기로 이어질 수 있고, 무엇보다 연구 결과에 대한 신뢰를 무너뜨린다.

이 장은 연구 윤리를 **매일의 연구 작업에서 내리는 결정**으로 다룬다. 무엇을 보고하는가, 누구를 저자로 올리는가, 어떤 데이터를 어떤 조건으로 쓰는가, AI 도구 사용을 어떻게 기록하고 밝히는가, 무엇을 어떻게 공개하는가. 마지막으로 이 결정들을 하나의 **재현 패키지**로 묶는다. 법률·규정의 세부는 나라·기관·학회마다 다르고 바뀐다. 이 장은 법률적 판단을 대신하지 않으며, 구체적인 규정은 소속 기관의 연구윤리 담당 부서와 해당 학회·저널의 원문에서 확인하는 절차로 쓴다.

## 학습 목표

- 연구 윤리의 기본 원칙을 지킨다
- 코드·데이터를 공개 가능한 수준으로 정리한다
- AI 도구 사용과 저자 기여를 기록하고 투명하게 밝힌다

## 연구 무결성

**왜 필요한가.** 과학은 다른 사람의 결과를 믿고 그 위에 쌓는 일이다. 모든 결과를 직접 확인할 수는 없으므로, 보고된 결과가 실제로 한 일을 정확히 나타낸다는 신뢰가 공동체 전체의 기반이다. 연구 무결성(research integrity)은 이 신뢰를 지키는 원칙이다. 2010년 세계연구진실성회의에서 나온 싱가포르 선언은 그 원칙을 정직(honesty), 책임(accountability), 다른 연구자에 대한 예의와 공정(professional courtesy and fairness), 다른 사람을 대신한 연구의 성실한 관리(good stewardship)로 요약한다. 유럽 학술원 연합(ALLEA)의 연구 진실성 행동 강령처럼 이를 구체화한 지침도 있다. 소속 기관의 연구윤리 규정은 대개 이런 지침을 바탕으로 한다.

**위조·변조·표절.** 가장 심각한 연구 부정으로 널리 꼽히는 세 가지다.

| 유형 | 뜻 | 연구 현장의 예 |
|---|---|---|
| 위조(fabrication) | 존재하지 않는 데이터·결과를 만들어 냄 | 돌리지 않은 실험의 숫자를 표에 채움, 나오지 않은 baseline 결과를 추정값으로 씀 |
| 변조(falsification) | 재료·장비·과정을 조작하거나 데이터·결과를 바꾸거나 빼서, 연구가 정확히 표현되지 않게 함 | 불리한 측정을 근거 없이 제거, 그림의 대비를 일부만 조정, 실패한 run을 말없이 제외 |
| 표절(plagiarism) | 다른 사람의 아이디어·문장·결과·코드를 출처 없이 자기 것처럼 씀 | 관련 연구 문단을 출처 없이 옮김, 공개 코드를 가져와 출처 표시 없이 "구현했다"고 씀 |

변조의 정의에 **빼는 것**이 들어간다는 점에 주의한다. 어떤 값을 바꾸지 않아도, 결과를 골라 보고해 연구의 실제 모습과 다르게 보이게 하면 변조에 가까워진다.

**결과 선택 보고의 문제.** 명백한 부정보다 훨씬 흔한 것이 회색 지대의 관행이다.

- **선택 보고(selective reporting).** seed 다섯 개 중 가장 좋은 seed, 데이터셋 열 개 중 이긴 세 개, 지표 다섯 개 중 좋아 보이는 두 개만 보고한다.
- **test set 재사용.** test 결과를 보면서 설정을 고른다. 학습에 쓰지 않았어도 선택에 쓰면 결과가 부풀려진다. 시도 횟수가 많을수록 커지는 이 편향은 [4.6장](../../04-git-and-agents/06-agentic-workflow/index.md)에서 계산으로 보였다.
- **결과를 본 뒤의 가설(HARKing).** 결과를 보고 만든 가설을 처음부터 세운 가설인 것처럼 쓴다(Kerr, 1998). 탐색에서 나온 가설은 탐색에서 나왔다고 쓰면 정당한 기여다.
- **조용한 계획 변경.** 분할·지표·전처리를 결과를 본 뒤 바꾸고 그 사실을 밝히지 않는다.

이 관행들의 공통점은 **각 단계는 정당해 보이지만 보고서가 실제 과정을 숨긴다**는 것이다. 해결책도 공통이다. 무엇을 시도했고 무엇을 뺐는지를 기록하고(23.7장), 계획에서 벗어난 것은 벗어났다고 쓴다(23.5장).

::quiz{id="selective-reporting"}

**재현 가능한 보고.** 결과를 정직하게 보고한다는 것은 구체적으로 다음을 뜻한다.

- 실행 횟수, 바꾼 무작위성(seed, 분할), 평균과 퍼짐(표준편차인지 신뢰구간인지 명시)을 쓴다([22.2장](../../22-experiment-operations/02-reproducibility/index.md)).
- 실패하거나 발산한 run을 뺐다면 그 수와 기준을 쓴다.
- 하이퍼파라미터 탐색의 범위와 예산을 baseline과 제안 방법에 똑같이 쓴다. baseline만 기본값으로 두는 것은 공정한 비교가 아니다.
- 이상치 제거·데이터 정제 규칙은 분석 전에 정하고, 규칙과 제거한 수를 보고한다.
- 부정적 결과와 한계를 쓴다. "이 방법은 X 조건에서는 개선이 없었다"는 다음 연구자의 시간을 아낀다.

:::note[분야 예시]
**전자현미경 영상**으로 미세구조를 분할하는 모델을 개발하는 연구에서, 논문 그림에 넣을 예시 영상을 고르는 것은 흔한 일이다. 문제는 고르는 기준이다. 모델이 잘 작동한 영상만 그림에 넣고 "대표적인 결과"라고 쓰면 독자는 평균적인 성능을 오해한다. 무작위로 고른 예시, 또는 오차 분포의 중앙값·하위 10% 위치의 예시를 함께 보이고 고른 방법을 캡션에 쓴다. 영상의 대비·밝기 조정은 영상 전체에 똑같이 적용하고, 조정했다는 사실을 방법 절에 쓴다. 일부 영역만 고치면 변조가 된다.
:::

## 저자와 인용

**왜 필요한가.** 저자 표시(authorship)는 **공로**와 **책임**을 함께 나타낸다. 저자 목록에 이름이 오르면 그 논문의 기여를 인정받는 동시에, 논문에 오류나 부정이 있을 때 책임을 진다. 기여한 사람을 빼는 것(유령 저자, ghost authorship)과 기여하지 않은 사람을 넣는 것(선물 저자, gift authorship)은 둘 다 이 연결을 끊는다.

**저자 기여 기준.** 분야마다 기준이 다르다. 의학 분야에서 널리 쓰이는 ICMJE 권고는 저자가 되려면 네 가지를 **모두** 충족해야 한다고 본다. 요지는 다음과 같다(정확한 문구는 ICMJE 원문에서 확인한다).

1. 연구의 구상·설계, 또는 데이터의 획득·분석·해석에 실질적으로 기여했다.
2. 원고를 쓰거나 중요한 지적 내용을 비판적으로 수정했다.
3. 출판될 최종본을 승인했다.
4. 연구의 모든 부분에 대해 책임을 지는 데 동의했다(정확성·무결성에 관한 질문이 제기되면 적절히 조사·해결되도록).

이 권고는 연구비 확보나 연구 그룹의 일반적인 지도**만으로는** 저자 자격이 되지 않는다고 보고, 그런 기여는 감사의 글(acknowledgments)에 적도록 한다. ML과 물리·화학 분야는 저마다 관행이 다르다. 대규모 실험 협업은 알파벳 순서의 긴 저자 목록을 쓰고, ML 논문은 "공동 제1저자(equal contribution)" 표시를 흔히 쓴다. 생명과학에서는 마지막 저자가 연구 책임자인 관행이 강하다. 관행이 다르기 때문에 **기준을 프로젝트 초기에 명시적으로 합의**하는 것이 중요하다. 학제 간 협업에서는 특히 그렇다(23.13장).

**기여의 기록.** 저자 목록의 순서만으로는 누가 무엇을 했는지 알 수 없다. CRediT(Contributor Roles Taxonomy)는 기여를 구상(conceptualization), 데이터 큐레이션(data curation), 형식적 분석(formal analysis), 연구비 확보(funding acquisition), 조사·실험 수행(investigation), 방법론(methodology), 프로젝트 관리(project administration), 자원 제공(resources), 소프트웨어(software), 지도(supervision), 검증(validation), 시각화(visualization), 초고 작성(writing – original draft), 검토·수정(writing – review & editing)의 14개 역할로 나눈다(Brand 외, 2015). 많은 저널이 이 분류로 기여 진술(contribution statement)을 받는다. CRediT는 저자 자격을 판정하는 기준이 아니라 **기여를 기록하는 어휘**다. 저자 기준(예: 위의 네 조건)과 함께 쓴다.

**인용 윤리.** 인용은 아이디어의 출처를 밝히고, 독자가 근거를 확인할 수 있게 한다.

- **읽은 것을 인용한다.** 다른 논문의 참고문헌 목록에서 옮긴 인용, AI 도구가 제시한 인용은 원문을 직접 확인한 뒤에만 쓴다. AI 도구는 존재하지 않는 논문이나 그 주장을 하지 않은 논문을 그럴듯하게 제시할 수 있다([4.3장](../../04-git-and-agents/03-ai-coding-tools/index.md)).
- **원 출처를 인용한다.** 개념을 처음 제안한 논문과, 실제로 쓴 구현·데이터의 출처를 구분해 둘 다 인용한다.
- **데이터와 소프트웨어도 인용한다.** 데이터셋과 라이브러리가 지정한 인용 형식(논문, DOI, `CITATION.cff` 파일 등)을 따른다.
- **문장을 옮기면 인용 부호를 쓴다.** 출처를 달아도 문장을 그대로 옮기고 인용 부호가 없으면 표절이다. 자신의 이전 논문의 문장을 그대로 재사용하는 것(text recycling)도 저널마다 규정이 있다.
- **인용을 부풀리지 않는다.** 관련 없는 자기 논문이나 동료 논문을 끼워 넣지 않는다. 심사자가 자기 논문 인용을 강요하는 것도 같은 문제다(23.11장).

## 데이터와 라이선스

**왜 필요한가.** AI 연구는 데이터에서 시작하고, 데이터에는 출처와 조건이 있다. 데이터의 이용 조건을 어기면 결과를 공개하지 못하거나, 공개한 뒤 내려야 하거나, 데이터를 제공한 사람들의 신뢰를 잃는다. 이 절은 연구 윤리 관점에서 무엇을 확인할지를 정리한다. 라이선스 조건의 세부, 가명화의 기술, 데이터 문서의 항목은 [15.5장](../../15-data/05-dataset-versioning/index.md)에서 다뤘다.

**데이터 이용 조건.** 데이터를 쓰기 전에 네 가지를 확인하고 기록한다.

| 질문 | 확인할 곳 | 흔한 오해 |
|---|---|---|
| 누가 어떻게 만들었는가(출처) | 데이터 논문, 데이터 카드, 제공 기관 | "논문에 쓰였으니 출처는 확인된 것이다" |
| 어떤 조건으로 쓸 수 있는가(라이선스·이용 약관) | 라이선스 파일, 이용 약관, 데이터 이용 계약 | "내려받을 수 있으면 써도 된다" |
| 사람에 관한 데이터라면 동의 범위는 무엇인가 | 연구 동의서, 연구윤리위원회(IRB) 승인 범위 | "익명화되어 있으니 동의 범위와 무관하다" |
| 재배포·파생물 공개가 허용되는가 | 라이선스의 재배포·파생물 조항 | "전처리했으니 새 데이터다" |

**공개 데이터라고 무엇이든 써도 되는 것은 아니다.** 공개(publicly available)는 접근할 수 있다는 뜻이지, 어떤 목적으로든 써도 된다는 뜻이 아니다. 비상업 조건, 재배포 금지, 특정 용도 금지, 인용 의무가 붙은 공개 데이터가 많다. 웹에서 수집한 데이터는 사이트의 이용 약관과 저작권이 따로 적용될 수 있다. 사람에 관한 데이터는 원래 동의받은 연구 목적 밖에서 쓰는 것이 허용되지 않을 수 있다. 판단이 어려우면 데이터 제공자와 소속 기관의 담당 부서(연구윤리위원회, 산학협력·법무 부서)에 확인한다.

**동의와 개인정보.** 사람에게서 나온 데이터(의료 기록, 생체 신호, 설문, 위치, 사진)는 다음을 지킨다.

- 연구윤리위원회의 승인 범위와 동의서의 이용 범위 안에서만 쓰고, 그 근거를 기록한다.
- 가명화는 익명화가 아니다. 준식별자의 조합으로 재식별될 수 있다(15.5장).
- 원본은 접근이 통제된 곳에서 다루고, 개인 기기나 외부 서비스로 옮기지 않는다. 외부 AI 서비스에 데이터를 붙여 넣는 것도 외부 전송이다.
- 모델 자체가 학습 데이터를 기억해 내보낼 수 있다는 점도 고려한다. 민감 데이터로 학습한 모델의 가중치 공개는 데이터 공개와 같은 수준으로 검토한다.

::quiz{id="public-data-use"}

**소프트웨어 라이선스 선택.** 공개하는 코드에는 라이선스를 붙인다. **라이선스 파일이 없는 공개 코드는 "누구나 써도 되는 코드"가 아니다.** 대부분의 법체계에서 저작물은 기본적으로 저작권자에게 권리가 있으므로, 명시적인 허락이 없으면 다른 사람이 안심하고 쓰거나 고치거나 재배포할 수 없다. 공개의 목적인 재사용이 막힌다.

라이선스는 크게 두 계열로 나뉜다(구체적인 조건은 각 라이선스 원문에서 확인한다).

| 계열 | 집필 시점 예시 | 성격 |
|---|---|---|
| 허용형(permissive) | MIT, BSD, Apache-2.0 | 저작권 표시를 유지하면 수정·재배포·상업적 이용을 넓게 허용 |
| 카피레프트(copyleft) | GPL 계열 | 파생 저작물을 배포할 때 같은 라이선스로 소스를 공개하도록 요구 |

선택할 때 확인할 것은 다음과 같다.

1. **소속 기관의 규정.** 연구 결과물의 지식재산권이 기관에 있을 수 있다. 공개 전에 기관의 절차를 확인한다.
2. **의존성과 가져온 코드의 라이선스.** 다른 저장소에서 가져온 코드는 그 라이선스를 따른다. 카피레프트 코드를 섞으면 전체 공개 조건이 달라질 수 있다.
3. **공동 연구 계약.** 산업체·외부 기관과의 협약이 공개 범위를 정하고 있을 수 있다.
4. **데이터·모델은 따로.** 코드 라이선스는 데이터와 모델 가중치에 자동으로 적용되지 않는다. 데이터와 문서에는 Creative Commons 계열(예: CC BY, CC0)을 흔히 쓰고, 공개 모델 가중치에는 용도 제한이 붙은 별도 라이선스가 쓰이기도 한다. 남의 모델을 미세조정했다면 원 모델의 라이선스를 확인한다.

:::note[분야 예시]
**배터리 제조사와의 공동 연구**에서 셀 수천 개의 공정 조건과 수명 데이터를 받았다. 계약상 원 데이터는 공개할 수 없다. 이때도 공개할 수 있는 것은 많다. 학습·평가 코드(라이선스 포함), 데이터의 스키마와 단위·결측 표기를 설명하는 데이터 문서, 같은 스키마의 합성 예시 데이터(15.6장), 그리고 "데이터 접근은 제공사와의 협약을 통해서만 가능하다"는 접근 안내다. 무엇을 공개할지는 논문을 쓰기 전에, 가능하면 계약 단계에서 합의한다.
:::

## AI 도구 사용

**왜 필요한가.** 생성형 AI 도구는 코드 작성, 문헌 요약, 문장 다듬기, 그림 생성, 데이터 분석에 두루 쓰인다. 도구를 쓰는 것 자체가 문제가 아니라, **무엇을 도구가 했는지 알 수 없게 되는 것**이 문제다. 독자와 심사자는 결과가 어떤 과정으로 나왔는지 알아야 그 결과를 평가할 수 있다.

**원칙.** 학회·저널의 정책은 다양하고 빠르게 바뀌지만, 공통된 방향이 있다.

- **AI 도구는 저자가 될 수 없다.** 출판 윤리 위원회(COPE)는 AI 도구가 제출한 연구에 책임을 질 수 없으므로 저자 요건을 충족할 수 없다는 입장을 밝혔다. 도구가 만든 부분을 포함해 원고 내용의 책임은 저자에게 있다.
- **사용을 밝힌다.** 어떤 도구를 어떤 목적으로 썼는지를 학회·저널이 정한 위치(방법 절, 감사의 글, 별도 진술)에 쓴다. 문법 교정 정도는 공개 대상에서 빼는 정책도 있고, 모든 사용을 밝히라는 정책도 있다. **투고처의 정책을 원문에서 확인한다.**
- **검증한다.** 도구가 만든 코드·수식·인용·요약은 직접 확인한 것만 쓴다. "AI가 쓴 코드였다"는 오류의 변명이 되지 않는다(4.3장).
- **기밀을 지킨다.** 공개되지 않은 데이터, 심사 중인 원고, 공동 연구자의 미발표 결과를 외부 AI 서비스에 넣는 것은 제3자에게 보내는 것이다. 데이터 계약과 기관 정책을 확인한다.
- **그림과 데이터는 특히 조심한다.** AI로 생성하거나 수정한 영상·그림을 실험 결과처럼 제시하는 것은 위조·변조가 된다. 예시 그림이나 개념도에 생성 도구를 썼다면 그 사실을 밝힌다.

**사용 기록.** 공개 의무가 어떻든, 자신을 위해 **사용 기록**을 남긴다. 논문을 쓸 때 무엇을 밝혀야 할지, 심사자가 물을 때 무엇을 답할지가 여기서 나온다.

| 날짜 | 도구(버전·설정) | 용도 | 입력한 것 | 결과를 어디에 썼나 | 어떻게 검증했나 |
|---|---|---|---|---|---|
| (예) 3월 4일 | 코딩 에이전트(버전 기록) | 전처리 스크립트 리팩터링 | 저장소 코드(데이터 제외) | `prep.py` | 리팩터링 전후 출력 해시 비교 |
| (예) 3월 9일 | 대화형 assistant(버전 기록) | 관련 연구 3절 문장 다듬기 | 직접 쓴 초고 | 논문 3절 | 인용 12개 원문 대조, 의미 변경 없는지 확인 |

코드 작업이라면 commit 기록이 사용 기록의 일부가 된다. 이 책의 저장소는 에이전트가 만든 commit 메시지 끝에 공동 작성자 표시와 작업 세션 링크를 남긴다(4.6장).

::quiz{id="ai-use-disclosure"}

## 오픈 사이언스

**왜 필요한가.** 오픈 사이언스(open science)는 연구의 산출물(논문, 코드, 데이터, 모델, 프로토콜)을 다른 사람이 확인하고 다시 쓸 수 있게 공개하는 실천이다. 공개된 코드와 데이터가 있으면 심사자와 독자가 결과를 확인하고, 결과가 재현되지 않을 때 원인을 찾고, 같은 출발점에서 다음 연구를 할 수 있다(1.6장). 데이터 공개의 원칙으로는 찾을 수 있고(Findable), 접근할 수 있고(Accessible), 상호 운용되고(Interoperable), 재사용할 수 있게(Reusable) 하라는 FAIR 원칙이 널리 쓰인다(Wilkinson 외, 2016).

**공개의 단위: 재현 패키지.** 공개는 저장소 링크 하나가 아니다. 다른 사람이 **같은 명령으로 같은 숫자를 다시 얻을 수 있는 묶음**이 공개의 단위다. 이 묶음을 재현 패키지(reproducibility package) 또는 artifact라 한다.

```text
my-paper-artifact/                 # 집필 시점 예시 구조
├── README.md          # 무엇을 재현하는가, 설치, 실행 명령, 기대 결과, 소요 시간·하드웨어
├── LICENSE            # 코드 라이선스
├── CITATION.cff       # 인용 방법
├── environment/       # lockfile 또는 컨테이너 정의(버전 고정)
├── data/README.md     # 데이터 출처, 라이선스, 받는 방법, manifest 해시, 분할 파일
├── configs/           # 논문의 각 표·그림에 대응하는 설정
├── scripts/           # 표·그림을 만드는 실행 스크립트
└── results/expected/  # 기대 결과(표의 숫자, 허용 변동 범위)
```

README에는 **논문의 각 표·그림과 그것을 만드는 명령의 대응표**를 둔다. "표 2: `bash scripts/table2.sh` (GPU 1장 기준 약 3시간, seed 5개 평균 ± 표준편차가 `results/expected/table2.csv`의 범위 안에 들어야 함)" 같은 형태다. 데이터를 공개할 수 없다면 `data/README.md`에 접근 신청 방법을 쓰고, 같은 스키마의 작은 합성 데이터로 파이프라인 전체가 돌아가는 것을 보인다.

**artifact 문서화.** 공개하는 데이터와 모델에는 문서를 붙인다. 데이터셋에는 동기·구성·수집 과정·권장 용도·한계를 담은 데이터시트(Gebru 외, 2021; 15.5장)를, 학습된 모델에는 의도한 용도, 평가 조건, 조건별 성능, 알려진 한계를 담은 모델 카드(Mitchell 외, 2019)를 쓴다. 특히 **권장하지 않는 용도**와 **평가하지 않은 조건**을 명시한다. 상온 데이터로만 학습한 배터리 모델이라면 "저온 조건은 평가하지 않았다"를 쓴다.

**공개의 한계: 이중 용도.** 공개가 언제나 이로운 것은 아니다. 이중 용도(dual use)는 이로운 목적으로 만든 연구가 해로운 목적으로도 쓰일 수 있는 성질이다. AI for Science에서는 이 위험이 구체적이다. Urbina 외(2022)는 신약 개발용 생성 모델의 목표를 독성 회피에서 독성 추구로 뒤집기만 해도 알려진 화학 작용제와 비슷한 분자가 대량으로 생성됨을 보고하며, 이 분야의 연구자들이 오용 가능성을 의식할 필요를 제기했다. 병원체, 화학 물질, 핵심 기반시설, 감시 기술에 관련된 연구에서 공개 전에 다음을 검토한다.

- **무엇이 위험을 실질적으로 높이는가.** 방법의 개념인가, 학습된 모델 가중치인가, 특정 생성 결과인가, 데이터인가. 위험은 대개 이 중 일부에 집중되어 있다.
- **공개의 형태.** 전부 공개와 비공개 사이에 단계가 있다. 방법과 평가는 공개하고 위험한 생성 결과는 빼기, 모델을 신원 확인된 연구자에게만 제공하기, 단계적으로 공개하기.
- **혼자 판단하지 않는다.** 소속 기관의 연구윤리·연구안전 담당 부서, 분야의 전문가, 해당 분야의 정부 규정을 확인한다. 생명과학처럼 이중 용도 연구에 대한 규정이 따로 있는 분야도 있다.

위험이 있다고 연구를 감추는 것만이 답은 아니다. 위험의 존재와 그에 대한 판단을 논문에 쓰는 것도 공동체에 대한 기여다.

:::note[분야 예시]
**유전체·의료 데이터**로 질병 위험을 예측하는 모델을 공개하려 한다. 코드와 평가 프로토콜은 그대로 공개할 수 있다. 학습된 가중치는 학습 데이터의 개인 정보를 기억해 드러낼 수 있으므로, 데이터와 같은 수준의 접근 통제(신청·승인 후 제공)를 검토한다. 모델 카드에는 학습 데이터의 인구 집단 구성과, 다른 집단에서 평가하지 않았다는 한계를 쓴다. 성능이 집단에 따라 다를 수 있다는 점을 쓰지 않으면, 그 모델은 평가하지 않은 집단에 대한 결정에 쓰일 수 있다.
:::

## 실습

자신의 프로젝트(또는 이 책의 앞 장에서 만든 실습 하나)를 공개 가능한 재현 패키지(README · 라이선스 · 데이터 안내 · 실행 스크립트)로 정리하고, 아래 체크리스트로 점검한다.

1. **패키지 구조.** 오픈 사이언스 절의 구조로 디렉터리를 정리한다. 논문(또는 보고서)의 표·그림마다 그것을 만드는 명령을 README의 대응표에 쓴다.
2. **라이선스.** 코드 라이선스를 정하고 `LICENSE` 파일을 넣는다. 가져온 코드와 의존성의 라이선스를 목록으로 만들어 충돌이 없는지 확인한다. 기관 규정을 확인한 결과를 기록한다.
3. **데이터 안내.** 사용한 데이터마다 출처·라이선스·동의 범위·재배포 가능 여부를 표로 쓴다. 재배포할 수 없는 데이터는 받는 방법과 전처리 스크립트, manifest 해시를 쓴다(15.5장).
4. **보고 점검.** 결과 표마다 실행 횟수, 바꾼 무작위성, 퍼짐의 종류, 제외한 run의 수와 기준이 적혀 있는지 확인한다. 실험 기록(23.7장)과 대조해 보고하지 않은 시도가 있다면 보고에 넣을지 판단하고 그 이유를 쓴다.
5. **기여와 AI 사용.** CRediT 역할로 기여 진술을 쓰고, AI 도구 사용 기록 표를 채운다.
6. **제3자 재현.** 동료에게 README만 주고 표 하나를 재현해 달라고 한다. 동료가 물어본 것이 README의 빈칸이다.

**연구 윤리 체크리스트.**

| 영역 | 항목 | 확인 |
|---|---|---|
| 무결성 | 모든 결과가 커밋된 코드와 기록된 실행에서 나왔다 | ☐ |
| | 제외한 데이터·run과 그 기준을 보고했다 | ☐ |
| | 계획에서 벗어난 분석을 밝혔다 | ☐ |
| | test set은 최종 평가에만 썼다(또는 사용 횟수를 밝혔다) | ☐ |
| 저자·인용 | 저자 기준을 합의했고 모든 저자가 기준을 충족한다 | ☐ |
| | 모든 인용을 원문에서 확인했다 | ☐ |
| | 데이터·소프트웨어를 지정된 형식으로 인용했다 | ☐ |
| 데이터 | 데이터마다 출처·라이선스·동의 범위를 기록했다 | ☐ |
| | 재배포 조건을 지켰다 | ☐ |
| | 개인정보·기밀이 공개물에 없다 | ☐ |
| AI 도구 | 사용 기록이 있고, 투고처 정책에 맞게 밝혔다 | ☐ |
| | AI가 만든 코드·인용·수식을 검증했다 | ☐ |
| 공개 | `LICENSE`가 있고 의존성과 충돌하지 않는다 | ☐ |
| | README의 명령으로 표·그림이 다시 만들어진다 | ☐ |
| | 데이터·모델 문서에 한계와 권장하지 않는 용도가 있다 | ☐ |

## 실패 사례

- **좋은 결과만 골라 보고하는 것.** seed 다섯 개 중 최고값, 데이터셋 열 개 중 이긴 셋. 각 선택은 사소해 보여도 보고서는 실제 연구와 다른 그림을 그린다. 모든 실행을 기록하고, 무엇을 왜 뺐는지 쓴다.
- **라이선스 없이 코드를 공개하는 것.** 라이선스가 없으면 다른 사람은 그 코드를 안심하고 쓰거나 고칠 수 없다. 공개의 목적이 사라진다. `LICENSE` 파일을 넣고, 가져온 코드의 라이선스와 맞는지 확인한다.
- **공개 데이터면 무엇이든 써도 된다고 여기는 것.** 접근할 수 있다는 것과 이용 조건은 별개다. 비상업 조건, 재배포 금지, 동의 범위를 확인하지 않은 파생 데이터셋은 공개하지 못하거나 내려야 한다.
- **AI 도구 사용을 밝히지 않는 것.** 도구가 쓴 문단과 코드가 섞인 원고를 아무 표시 없이 제출하면, 투고처 정책 위반이 될 수 있고 오류가 드러났을 때 경위를 설명할 수 없다. 사용 기록을 남기고 정책에 맞게 밝힌다.
- **기여 없는 사람을 저자로 넣는 것.** 연구실 관행이나 관계 때문에 기여하지 않은 사람을 저자로 넣으면, 그 사람은 확인하지 않은 논문에 책임을 지게 되고 실제 기여자의 공로는 희석된다. 저자 기준을 미리 합의하고, 기준에 미치지 않는 기여는 감사의 글에 쓴다.

## 통과 기준

- 실습의 연구 윤리 체크리스트를 모두 통과한 재현 패키지를 만든다. 동료가 README만 보고 표 하나 이상을 보고된 변동 범위 안에서 재현한다.
- 패키지에 사용한 데이터마다 출처·라이선스·동의 범위·재배포 가능 여부를 적은 표와, 코드 및 의존성의 라이선스 목록이 있다.
- CRediT 역할로 쓴 기여 진술과, 도구·용도·검증 방법을 적은 AI 도구 사용 기록을 남긴다.
